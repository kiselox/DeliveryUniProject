# AI Coding Instructions & System Guide

Этот файл является главным техническим руководством для ИИ-агента, работающего с кодовой базой проекта **POLONEZ Delivery**. Перед внесением любых изменений внимательно изучите стек, архитектурный паттерн и строгие правила разработки.

---

## 🛠️ 1. Технологический Стек (Tech Stack)

Проект представляет собой интерактивный симулятор службы доставки в г. Познань с разделением ролей (Клиент, Курьер, Поддержка/Админ) и интерактивными картами.

### Frontend:
* **React 19** (Functional Components + Hooks).
* **Vite 8** — быстрый и легкий сборщик клиентской части.
* **React Router v7** — клиентская маршрутизация по ролям (`/`, `/customer/:id`, `/courier/:id`, `/admin`).
* **React Query v5** (`@tanstack/react-query`) — кэширование, мутации данных и автообновление интерфейса в реальном времени с помощью пуллинга (`refetchInterval`).
* **Leaflet 1.9** — интерактивные карты, рендеринг гео-маркеров и маршрутных полилиний OpenStreetMap.
* **Axios** — HTTP-клиент для обмена данными с бэкендом.
* **Styling**: Чистый **Vanilla CSS** (глобальные CSS-переменные в `:root`, флексы, гриды, выделенные CSS-файлы для страниц и компонентов). В проекте **НЕ используется TailwindCSS**. Использование **inline-стилей (`style={{...}}`) строго ограничено**: они допускаются только для динамических значений, рассчитываемых на лету в JS (например, прогресс-бары, динамические сдвиги или передача CSS-переменных через `style`). Статическое оформление должно быть строго в CSS.

### Backend:
* **Node.js** + **Express** — сервер приложений REST API.
* **Двухрежимная база данных (Dual Mode DB)**:
  1. **PostgreSQL + PostGIS** (при наличии `DATABASE_URL`) — промышленный режим с географическими точками (`GEOGRAPHY(Point, 4326)`) для точных пространственных SQL-запросов.
  2. **JSON File Fallback** (по умолчанию) — локальная файловая сериализация в `db.json` с in-memory кэшированием.
* **Познаньский геокодер (Street Geocoder)**: Серверный нормализатор польских букв (`ł -> l`, `ó -> o` и т.д.) со встроенным словарем координат ключевых улиц Познани (Półwiejska, Garbary, Jeżyce, CDV и др.).
* **Формула гаверсинусов (Haversine formula)**: Математическое вычисление расстояния между точками на сфере в метрах для JS-режима бэкенда.

│   │
│   ├── components/           # Чистые переиспользуемые UI-компоненты (Presenter-only)
│   │   ├── Header.jsx        # Шапка личного кабинета с поиском и адресом

## ⚡ 3. Строгие правила кодирования (AI Coding Rules)

Для сохранения чистоты и работоспособности проекта ИИ-агент должен неукоснительно соблюдать следующие **8 правил**:

### Rule 1: Функциональный React 19 и Hooks-Only
Мы пишем исключительно функциональные компоненты React с использованием хуков (`useState`, `useEffect`, `useMemo`). Классовые компоненты строго запрещены. Компоненты экспортируются по умолчанию (`export default`).

### Rule 2: Использование Vanilla CSS и строгое ограничение Inline-стилей
В проекте **запрещено внедрять или использовать TailwindCSS** (если этого явно не потребовал пользователь). 
* Все статическое оформление, разметка сеток (`grid`, `flex`), отступы, цвета, ховеры, тени и анимации должны описываться в CSS-файлах (глобальный `src/index.css` или выделенные CSS-файлы страниц/компонентов).
* **Inline-стили (`style={{ ... }}`) строго ограничены** и допускаются исключительно для динамически вычисляемых в JS значений, которые невозможно задать статическим классом (например, `style={{ width: `${progress}%` }}`, расчет позиции элементов или передача JS-стейта через CSS-переменные). Статическая стилизация через inline-стили запрещена.

### Rule 3: Работа с сервером только через React Query v5
Прямые вызовы асинхронных методов в жизненном цикле компонентов запрещены. 
* Для получения данных используйте хук `useQuery`.
* Для отправки, удаления и обновления данных используйте `useMutation`.
* Для мониторинга критических процессов реального времени (обновление списка заказов курьера, пульт админа, настройки надбавок) обязательно настраивайте интервальный опрос через параметр `refetchInterval` (в пределах 3000–5000 мс).

### Rule 4: Делегирование HTTP-запросов в слой Services
Компоненты не должны знать о деталях HTTP-запросов или библиотеке Axios. Все запросы обязаны выполняться через экспортируемые сервисные объекты из папки `src/services/` (например, `orderServices.createOrder()`), которые ссылаются на единый настроенный инстанс `api.js`.

### Rule 5: Управление жизненным циклом слоев Leaflet (Предотвращение утечек)
При работе с Leaflet (`L.map`, `L.marker`, `L.polyline`) внутри компонентов карт (`Courier.jsx`, `CustomerMenu.jsx`):
* Всегда оборачивайте инициализацию карты в проверку существования контейнера.
* При размонтировании компонента или изменении гео-точек обязательно очищайте старые слои (`marker.remove()`, `routeLine.remove()`, `map.removeLayer()`).
* Для рендеринга курьера, ресторанов и клиентов используйте векторизованные кастомные иконки (`L.divIcon`), переопределяя стандартные стили Leaflet через глобальный CSS.

### Rule 6: Синхронное развитие PostgreSQL (PostGIS) и JSON-бэкенда
При расширении модели данных (например, добавление новых полей в заказ, курьера или настройки):
* Добавьте миграции создания колонок в метод `initPostgresDb()` в `server.js` (`ALTER TABLE orders ADD COLUMN IF NOT EXISTS ...`).
* Поддержите чтение и запись этих полей в блоке логики JSON-файла (`loadLocalDb()`, `saveLocalDb()`, парсинг входящих объектов).
* Обеспечьте корректный фолбек в кодовой базе сервера, если PostgreSQL недоступен.

### Rule 7: Безопасный рендеринг полей с дефолтными значениями
Поскольку база данных содержит исторические заказы и седы, в которых могут отсутствовать новые расширенные поля (такие как `house`, `apartment`, `floor`, `phone`, `notes` или `coefficient`), при выводе информации на экран **всегда** используйте защитные операторы или оператор нулевого слияния:
`{order.house || '—'}` или `{order.phone ?? 'Не указан'}`.

### Rule 8: Строгая компонентность и модульность (Strict Component Modularity)
Мы пишем проект исключительно компонентно. Никаких гигантских монолитных файлов.
* Каждый логически обособленный элемент интерфейса (форма заказа, шапка, карточка, переключатель, модальное окно, фильтр) должен быть вынесен в отдельный функциональный React-компонент.
* Локальные вспомогательные компоненты страниц хранятся в подпапках `components/` внутри директории соответствующей страницы (например, `src/pages/Customer/components/`).
* Компоненты общего назначения, используемые более чем на одной странице, строго переносятся в глобальную директорию `src/components/`.
* При реализации новых функций запрещено писать ad-hoc разметку в теле страницы — сначала спроектируйте переиспользуемые мелкие компоненты, а затем соберите их в единый интерфейс.

## 🎯 4. Справочник API эндпоинтов для интеграции

Используйте эти пути при расширении функционала:
* `GET /settings` / `POST /settings` — Чтение и запись системных тарифов для разных классов транспорта (`pricePerKm`, `scooterPricePerKm`, `carPricePerKm`) и погодной надбавки.
* `GET /orders` — Получение списка всех заказов.
* `POST /orders` — Создание нового заказа с гео-координатами и параметрами адреса.
* `PATCH /orders/:id` — Обновление статуса заказа (`"Ready for Pickup"`, `"Accepted"`, `"Delivering"`, `"Delivered"`), привязка курьера (`courierId`) или изменение спроса (`coefficient`).
* `GET /vendors` — Список ресторанов Познани.
